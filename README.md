# Amg — пайплайн автогенерации коротких видео

Автоматическая сборка коротких вертикальных роликов (Instagram Reels, YouTube
Shorts, TikTok, VK Клипы) под несколько продуктов сразу: сценарий генерирует
**OpenRouter**, озвучку и иллюстрации — **Kie.ai** (модели ElevenLabs и
Nano Banana под одним ключом), финальный ролик собирает **Remotion** (видео
как React-компоненты).

## Как это работает

1. `npm run generate -- "бриф о продукте и посыле видео"` —
   - OpenRouter (по умолчанию Claude Sonnet 5) генерирует сценарий: заголовок + сцены
     (текст на экране + текст озвучки);
   - Kie.ai озвучивает текст каждой сцены моделью ElevenLabs и сохраняет
     `.mp3` в `public/audio/`;
   - Kie.ai генерирует иллюстрацию для каждой сцены (по умолчанию
     Nano Banana Edit) и сохраняет `.png` в `public/images/` — в запрос
     передаётся картинка предыдущей сцены, чтобы стиль держался из сцены в
     сцену, а в хуке и финале ещё и эталон внешности маскота;
   - длительность каждой сцены рассчитывается по реальной длине аудио и
     записывается вместе со сценарием в `data/video-data.json`.
2. `npm run render` — Remotion рендерит `data/video-data.json` в
   `out/video.mp4`.
3. `npm run preview` — открывает Remotion Studio для визуальной проверки/
   правки шаблона в браузере.

## Про повторение стиля готового видео

Готового сервиса «загрузи видео — получи точную копию дизайна и анимации»
не существует: переходы, тайминг, шрифты и раскадровку нужно один раз
воссоздать вручную (или получить у агентства исходники монтажа) в виде
Remotion-шаблона. Дальше шаблон переиспользуется программно для любого
количества роликов — в этом и есть автоматизация.

По присланному референсу воссоздан "каркас" ролика в `src/remotion/Scene.tsx`:
белый фон, скруглённая карточка в толстой чёрной рамке, под ней — субтитры по
словам жирным узким гротеском (Oswald 700, как в референсе). Статической
подписи под картинкой больше нет: весь текст в кадре несут субтитры, а `caption`
из сценария осталась только названием сцены для согласования в чате.
Геометрия каркаса не подбиралась на глаз, а снята с кадров референса (1440×2560)
и пересчитана на 1080×1920: карточка 75.4% ширины, пропорции 0.757, верх на
10.9% высоты, рамка 14 px. Все эти числа и положение субтитров лежат в одном
модуле `src/remotion/layout.ts` — не для красоты: карточка растёт под пропорции
картинки, и картинки 9:16 растягивали её ровно на строку субтитров, рамка
ложилась поверх букв. Теперь предельная высота карточки считается из положения
строки (минимум 3% высоты кадра просвета), а у моделей просим картинку 3:4
(≈0.757, как в референсе) — тогда она и не обрезается, и в карточку попадает
целиком. Инвариант «низ карточки выше верха заглавных» закреплён тестом.
Анимация: появление карточки одним из вариантов (проявление, выезд, зум-удар,
покачивание, влёт повёрнутой карточкой, тасовка колодой, зум-блюр во весь кадр,
рваная шторка) и уход другим (смятие с перекосом, сжатие, схлопывание по
горизонтали, увод вверх), звук на каждом стыке. Набор перебирается по номеру сцены, поэтому подряд идущие сцены
двигаются по-разному, а рендер остаётся повторяемым — см.
`src/remotion/transitions.ts`.

**Наезда на картинку внутри карточки нет намеренно.** В референсе иллюстрация
стоит мёртво: я мерил покадровую разницу внутри рамки — 0.00–0.15 из 255 на
протяжении полутора секунд. Вся жизнь кадра там в стыках и в маскоте, а не в
ползающей картинке; с нашим прежним наездом (зум 13% за сцену) мягкий стык
переставал читаться как мягкий. Вернуть можно, но это осознанное расхождение
с образцом.

**Зум-блюр во весь кадр** (`zoomIn`) — самая частая механика в референсе, три
стыка из девяти. Новая сцена приходит размазанной на весь экран и садится в
рамку. Настоящего радиального блюра в CSS нет: `filter: blur()` размывает
равномерно и даёт мутное пятно вместо полос от центра, поэтому смаз собирается
стопкой копий картинки с растущим масштабом — классический приём, шесть слоёв
уже читаются как полосы.

**Рваная шторка** (`tornWipe`) — новая картинка наползает на старую неровным
краем. Прямую границу дал бы `wipe` из библиотеки переходов; неровную рисуем
сами через `clip-path: polygon()`, где точки границы смещены суммой трёх
синусов от индекса. Именно синусов, а не `Math.random()`: рендер должен быть
повторяемым, иначе каждый прогон давал бы другой кадр.

Оба этих появления закрывают кадр целиком, поэтому им отключается и кроссфейд,
и уход предыдущей сцены (`coversFrame()`) — ровно как библиотечным переходам.
Без этого уходящая карточка мялась прямо под наползающим рваным краем: два
движения одновременно.

**Графических акцентов вокруг карточки нет** — искры, звёзды, стрелки и кольца
(`src/remotion/Accents.tsx`) выключены по умолчанию. Это была моя выдумка, а не
замер: в присланном референсе полоса над карточкой пуста на 259 проверенных
кадрах всех семи частей. Редкие «непустые» кадры при разборе оказались
зум-блюром на стыке, который закрывает кадр целиком, — то есть не украшением, а
переходом. Код оставлен: приём сам по себе рабочий, и `accentsEnabled: true` в
данных ролика его возвращает, но это будет осознанным отходом от образца.

**Сцена без карточки: маскот во весь рост на белом** (`src/remotion/mascot.ts`,
`MASCOT_SCENES`). Это приём из референса, которого у нас не было вовсе: там
карточка на такой сцене исчезает совсем, и персонаж стоит прямо на белом фоне.
Мы же маскота всегда прятали ВНУТРЬ рамки — отсюда и однообразие: рамка не
ломалась ни разу за ролик.

Числа сняты с установившегося кадра: фигура занимает 60.6% высоты, верх на
14.4%, по центру, рамки нет. Наш рендер сходится по высоте, верху и низу до
0.1%; по ширине шире (71% против 63%), потому что у нашего эталона скрещённые
руки, а в референсе поза уже — подгонять обе стороны одним кропом нельзя, и
ведём по высоте: она задаёт, насколько крупно читается лицо.

Такой сцене **не нужна иллюстрация** — рисовать нечего. Это и экономия одной
генерации на ролик, и порядок в согласовании: иначе картинка попадала бы в
чат на утверждение, а в ролик не входила.

Одна сцена на ролик по умолчанию, и это финал — там маскот обращается к
зрителю с призывом. Приём сильный, но от повторения стирается; в референсе он
тоже встречается один раз.

Отдельно стоит записать про **осторожность с кадрами перехода**. Сначала я
прочитал этот же приём неверно — принял кадр на 3.0 с за композицию и написал,
что «карточка повёрнута, а иллюстрация выходит за рамку». На полном
разрешении оказалось, что иллюстрация целиком внутри рамки, а поворот — это
середина схлопывания карточки перед сценой-маскотом. Вывод простой: измерять
надо установившийся кадр, а переходные отбрасывать.

**Сквозной объект через стык** (`overlay.acrossCut`) — предмет остаётся висеть
неподвижно, пока картинка под ним меняется целиком, и связывает две сцены в
одну мысль. Рисуется отдельным слоем **после** всех сцен: внутри своей сцены он
не работает, потому что следующая сцена — это `Sequence` ниже по дереву, она
рисуется выше и закрывала бы объект ровно на том стыке, который он должен
пережить. Ставит признак сценарист, и в промпте он назван редким приёмом:
объект, оставшийся там, где он уже ни при чём, выглядит поломкой.

**Брендовая концовка** (`src/remotion/Outro.tsx`) — последний кадр ролика:
тёмная плашка со скруглёнными углами, название бренда и строчка помельче.
Приходит тем же зум-блюром, что и сцены, чтобы не выглядеть приклеенной от
другого ролика. Настраивается через `BRAND_NAME` / `BRAND_TAGLINE` /
`BRAND_LOGO_FILE` / `OUTRO_SECONDS`; пустое `BRAND_NAME` отключает её целиком.

Логотип лежит в `public/brand/logo.png` — он вырезан из концовки присланного
референса (кадр 1440×2562, круг 398 px), фон убран `colorkey` по цвету плашки,
поэтому файл работает на любом фоне. Геометрия концовки снята оттуда же:
плашка 75.1% ширины кадра, пропорции 1.294, верх на 24% высоты, логотип 36.8%
ширины плашки, цвет `#212d3a` взят пипеткой.

Подключается логотип **только если файл действительно на месте** — проверка в
`buildOutro()`, и она же закрыта тестом. Ссылка на отсутствующий файл уронила
бы рендер на последнем кадре, то есть после всей дорогой работы.

Текст концовки не переносится, а ужимается по ширине: наш Oswald шире шрифта
из референса (то же расхождение, что и в субтитрах), и подпись, умещавшаяся
там в одну строку, у нас переносилась и обрезалась нижним краем плашки.

**Длина стыка своя у каждого перехода** и задаётся в секундах, а не в кадрах
(`MIX.sharpTransitionSeconds` / `softTransitionSeconds`): резкие механики в
референсе укладываются в 0.28–0.32 с, а мягкий кроссфейд идёт заметно дольше,
0.47 с. Раньше у нас все стыки были одной длины, и мягкий читался как резкий.

Звуки на стыках — щелчок, хлопок, снап и удар: атака в единицы миллисекунд
(это и есть «резко»), но с слышимым хвостом на 240-600 мс — с совсем коротким
спадом звук проскакивал под озвучкой незаметно. Они синтезируются
`node scripts/build-sfx.mjs` через ffmpeg и лежат в `public/sfx` в формате wav.
Соседние стыки никогда не получают один и тот же звук.

**Из референса эти звуки не взять — и, как выяснилось, даже не измерить.**

Взять напрямую нельзя, и это проверено по настоящим склейкам, а не на глаз:
моменты склеек найдены по видео (`select='gt(scene,0.25)'`), и в каждом из них
прирост энергии в 1-8 кГц составляет всего +0.8…+6.6 дБ, а речь в тот же момент
на 5-15 дБ ГРОМЧЕ самого стингера. Вырезанное окно содержало бы звук стыка
вместе с чужим голосом — под нашей озвучкой это звучало бы как двойная речь.
Ни одной склейки, попавшей в настоящую паузу, в семи частях нет.

Здесь была ошибка, и её стоит держать на виду. Сначала в этом разделе стояло
«тембр выверен по референсу измерением»: спектральным вычитанием (мощность в
момент события минус мощность фона рядом) по девяти стыкам выходило «центр
900-6000 Гц, 8-61% энергии ниже 300 Гц». Разброс 8-61% сам по себе должен был
насторожить — у одного и того же приёма так не бывает.

Проверка это подтвердила. Тот же метод прогнали по НАШЕМУ ролику, где известно,
какие звуки стоят на склейках. Он «восстановил» 40.7% энергии в 20-120 Гц и
42.3% в 500-1000 Гц — а в наших файлах `click` держит 42% и 44% в 1-4 кГц,
`clap` 72% в 20-120, `snap` 53% в 120-250. То есть метод не узнал даже то, что
сам же и слышал. Причина простая: речь за 100 миллисекунд не постоянна, слог
меняет спектр сильнее, чем добавляет тихий стингер, и вычитание соседних окон
достаёт голос, а не звук.

Что из этого остаётся в силе: у первых версий наших звуков низа не было вовсе
(`highpass=700` у `click`, полосовые от 1900 и 4200 Гц у `clap` и `snap`) — и
звучали они «пластиково», как щелчок мышью. Низкая составляющая (`body`) это
исправила, и по-прежнему это **шумовой всплеск под лоупассом, а не чистый
синус**: синус занимает несколько бинов спектра и основания не даёт. Но выбор
величины низа — решение на слух и по смыслу приёма, а не подгонка под обмер
референса, и выдавать его за обмер было неправильно.

Что действительно проверено тестами и остаётся проверяемым: атака (не дольше
15 мс), одинаковая громкость всех звуков, различие тембров между собой и то,
что соседние стыки не получают один и тот же звук.

Громкость выравнивается **отдельным проходом по готовым файлам** (−17 dB RMS).
Раньше она держалась на подобранных вручную `volume=` в каждом звуке и
разъезжалась при любой правке фильтров — после добавления низа разброс дошёл
до 5 dB. Оба свойства закрыты тестом: `test:timing` считает спектр прямым ДПФ
и проверяет и профиль, и разброс громкости.

Уровни всех слоёв собраны в `src/remotion/mix.ts`: озвучка 1.0, стык 0.75,
звук хука 0.5, музыка 0.145 — она фон под речью, а не отдельный слой. Там же
длина стыков в секундах: она же длительность анимации ухода, поэтому обе
величины держим в пределах паузы после реплики (0.4-0.5 с).

### Пауза между сценами: почему её держали и почему больше не держим

В ролике набегало **10 секунд тишины — 13% времени**, при том что в референсе
пауз около 2%. Речь из-за этого шла рывками. Причин было две, и обе наши.

**Первая: запас 0.4 с после каждой реплики.** Он стоял не просто так — считалось,
что стык обязан лечь в тишину после фразы, иначе переход придётся на речь. Я это
проверил и утверждение оказалось неверным: из девяти стыков присланного
референса **семь приходятся ровно на речь** — диктор в этот момент говорит на
12-25 дБ громче своего же фона. Именно поэтому там речь и льётся непрерывно.
Запас снижен до 0.15 с.

**Вторая: хвост тишины от самого синтезатора.** Он приходил поверх нашего запаса
и складывался с ним. Теперь срезается (`trimTrailingSilence`), но только с
КОНЦА: начало трогать нельзя, к нему привязаны тайминги слов от провайдера, и
сдвиг развалил бы субтитры. Порог −45 дБ, 60 мс хвоста остаётся — срез вплотную
к последнему звуку слышен как обрубленное слово.

Побочный эффект, который стоит знать: запас работал ещё и амортизатором бюджета —
подгонка снимала по 0.28 с со сцены, до 4 секунд на ролик. Теперь снимать почти
нечего, и переполнение честно показывается вместо того, чтобы растягиваться
паузами. Это правильнее: лишние секунды надо убирать из сценария, а не прятать в
тишине, и проверка ритма ловит перебор слов ещё до генерации.

### Появление объекта: центр кадра и свой звук

Объект прилетал в угол и медленно сползал вниз — приём был задуман как «купюры
падают», но у предмета, стоящего сбоку, чтение получается другое: его легко
пропустить, особенно в хуке, где решают первые секунды. Теперь три изменения:

- **Центр вместо углов.** Чередование углов по индексу сцены убрано, объект
  всегда по центру. Угловые якоря остались в схеме — они осмысленны, когда
  предмет не должен спорить с сюжетом иллюстрации, и данные с ними рисуются
  как раньше. Замечу точность: центр — это центр КАРТОЧКИ (50% ширины, 38.9%
  высоты кадра), а не геометрический центр кадра. Объект живёт внутри карточки,
  её рамка его подрезает, и это специально: вынесенный на белое поле он читался
  бы наклейкой поверх ролика, а не частью кадра.
- **Снос вниз убран совсем.** Осталось покачивание ±2.5° — его хватает, чтобы
  предмет не выглядел приклеенным. Проверено рендером: на кадрах 45, 100 и 200
  объект стоит ровно в одной точке, раньше к концу сцены он уезжал на 3% высоты.
- **Свой звук — `pop`.** Отдельный, а не один из четырёх стыковых: объект
  прилетает ВНУТРИ сцены, и знакомый щелчок склейки заставил бы слышать стык
  там, где его нет. Центр полосы 1044 Гц — между хлопком (832) и щелчком (1756),
  атака 10 мс, спад 140 мс, громкость выровнена тем же проходом, что и остальные
  (разброс по набору 1.2 dB). В миксе он тише стыка: 0.55 против 0.75.

Звук ставится на уровне композиции, а не внутри `Overlay`: там кадр
отсчитывается от начала сцены, и вложенная `Sequence` со звуком жила бы в другой
системе координат. Проверено не «должно играть», а вычитанием двух рендеров —
одного с объектом, другого без: разница содержит ровно один звук длиной 0.29 с,
начинающийся там, где заявлено (расхождение 50 мс — задержка AAC-кодера).

### Автопилот

`/autopilot` — конвейер идёт без кнопок между шагами: сценарий, картинки,
озвучка, сборка, готовое видео. Настройка живёт в сессии и переживает `/new`, как
голос и модели. `/autopilot off` возвращает согласования, `/autopilot` без
аргумента переключает. Состояние видно в `/start`.

Быстрее всего с профилем: `/profiles` → выбрать → отправить тему (или `/skip`) →
ждать видео. Два касания на ролик.

**Проверки автопилот не отменяет.** Структурные (ритм, длина хука, реклама не в
финале) и критик по чек-листу работают как раньше. Более того, ради автопилота
пришлось закрыть дыру: правка сценария — это ПРОСЬБА к модели, а не гарантия, а
бот писал «✏️ Переписал: ритм» и на этом успокаивался, то есть утверждал
результат, не проверив его. Теперь после автоправки структурные проверки
прогоняются заново (они бесплатные, в отличие от критика) и возвращаются полем
`remaining`. В обычном режиме это предупреждение, на автопилоте — **единственное
условие остановки**: цепочка встаёт на сценарии, до трат на картинки и озвучку.

**Чего автопилот лишает — и это стоит сказать прямо.** Взгляда человека на
сценарий перед отрисовкой. Ритм и структуру автоматика проверяет, а ведёт ли тема
к продукту — нет: ролик про энергопотребление дата-центров с финалом «попробуй
наш бот для картинок» проходит все проверки и при этом не продаёт. В обычном
режиме бот прямо просит это проверить, на автопилоте — не спрашивает. Поэтому при
включении он перечисляет, что именно перестаёт спрашивать, и предупреждает, если
включено оживление кадров (самая дорогая часть тоже пойдёт без подтверждения).

Сцепка шагов живёт в `src/bot/autopilot.ts` отдельным файлом, потому что в ней два
неочевидных условия, и каждое могло бы стоить ролика: продолжать только если
предыдущий шаг ПРОШЁЛ (обёртка `withGeneration` ловит ошибки сама и наружу
исключение не выпускает, поэтому по факту возврата судить нельзя) и только если
диалог не ждёт ввода (шаг сценария мог сам остановить автопилот). Вызывается
цепочка снаружи `withGeneration`: внутри флаг генерации ещё поднят, и вложенный
шаг ответил бы «уже идёт другая генерация». Всё это закрыто тестами в `test:bot`.

### Движение в кадре: смена картинки внутри сцены

Обмер покадровой разницы показал разрыв, которого не было видно на глаз: в
референсе кадр «живёт» **15% времени** (22 движения за 62 с), в нашем ролике —
**4%** (7 движений за 71 с). Стыки при этом у нас в порядке: в референсе они
длятся 0.13-0.57 с, у нас 0.3 и 0.45, и главный их механизм — зум с моторным
смазом — давно есть (`zoomIn`, в цикле дважды). Разрыв был весь внутри сцен.

В референсе внутри сцены **иллюстрация меняется на другую** — 13 раз за 62
секунды, то есть примерно раз на сцену. Видно два механизма: картинка уезжает
вниз и растворяется, а под ней открывается следующая (46.5 с), либо старая
сдирается как страница, загибаясь (11.9 с). Реализован первый: он даёт почти
весь эффект, а загиб бумаги потребовал бы маски с деформацией. Длительность 0.5 с
— по обмеру там 0.5-0.9 с.

Как это устроено. Сценарий получил поле `swap: {scene, word}`: описание ВТОРОЙ
картинки и слово реплики, на котором происходит смена. Правило в промпте требует
не «то же, но крупнее», а следствие или противоположность первой картинки —
было засохшее поле, стало полито; был счёт на миллион, стала пустая касса. Тогда
смена работает доводом, а не перелистыванием. Вторая картинка рисуется ПОСЛЕ
первой и от неё же (первая уходит в модель эталоном): они видны почти
одновременно, и расхождение стиля здесь заметнее, чем между сценами.

В кадре вторая картинка лежит НЕПОДВИЖНО под первой, а уезжает и гаснет первая —
именно так в референсе. Растворение начинается позже съезда (с 45% движения):
если гасить сразу, смена читается как простое растворение, а не как «сдвинули и
убрали». Смену не пускаем на участок ухода сцены: два движения подряд — картинка
вниз, а за ней вся карточка — читаются как сбой; если слово попало слишком близко
к концу, смены просто не будет.

Цена: вторая картинка на сцену, где приём применён (промпт просит примерно каждую
третью). Против клипов Seedance это копейки.

**И почему появляющихся объектов в роликах почти не было.** Механизм `overlay`
работал, а поле приходило пустым: в примере промпта (`STYLE_EXAMPLE`) на 13 сцен
не было ни одного `overlay`, при правиле «объект нужен примерно в половине сцен».
Модель копирует пример, а не правило — ровно та же ошибка, что была с ритмом
сцен. Теперь в примере 6 объектов и 4 смены картинки на 13 сцен, включая один
`acrossCut`. Заодно бот перед сборкой пишет в чат, сколько в ролике смен и
объектов, и предупреждает, если не набралось ни одного: узнавать о статичном
ролике лучше до рендера, чем после просмотра.

### Второй референс: что оказалось правилом, а что случайностью

Прислали второй ролик того же агентства (62 с, 1440×2560, тот же джин, та же
брендовая плашка PRO NEIRO). Он ценен не сам по себе, а как контроль: то, что
совпало с первым, — приём, который стоит держать в коде; то, что разошлось, —
свобода, которую мы зря считали ограничением. Ролик прислан пережатым онлайн-
сервисом (внизу водяной знак), поэтому тонкие цвета и частота кадров по нему
недостоверны — геометрия, тайминги, громкость и структура переживают пережатие
спокойно.

**Совпало — значит правило.** Карточка: ширина 75-77% кадра, верх на 10.5-11.1%,
пропорции 0.757 (ровно 3:4), рамка около 20 px при ширине 1440. Подпись: высота
заглавных 4.1-4.2% высоты кадра (78-81 px на 1080), по центру, базовая линия на
23% от низа. Одно слово в кадре, крупно, чёрным по белому, без плашки. Фон —
чистый белый (в первом референсе он меряется 253.5±2.2 — это шум кодека вокруг
белого, а не кремовый оттенок; во втором ровно 255). Сцена без карточки с
маскотом во весь рост — есть в обоих. Наши константы по всем этим пунктам
совпали с обмером, кроме двух — см. ниже.

**Совпало и в звуке.** Фоновой музыки нет и во втором: пауз длиннее 150 мс всего
четыре на 62 секунды, в них низы падают на 13-56 дБ, а пик низов каждый раз на
другой частоте (82, 129, 234 Гц) — то есть это остатки голоса, а не подложка.
Дорожка почти моно (корреляция каналов +0.994). Громкость −9.9 LUFS при разбросе
2.1 LU — та же «радийная» плотность, что у первого (−9.8…−12.2 LUFS). Наш целевой
−12 — тихий край этого семейства, и это осознанно: площадки всё равно приводят к
своей норме.

**Разошлось с нами — наши ошибки, обе исправлены.** Скругление карточки: у нас
стояло 26 px на 1080, в обоих референсах 15 (19-22 px при ширине 1440, восемь
кадров, разброс 14.5-16.6). На сравнении кадров рядом это было видно глазом:
наша карточка читалась скруглённой плашкой, референсная — рамкой. И знаки
препинания: в 14 подписях второго референса и во всех измеренных подписях первого
нет ни точки, ни запятой, ни вопросительного знака, а у нас в кадр попадало
«ДА?», «МОДЕЛЕЙ.», «ТОМ,». Теперь края слова чистятся, но только края: «0,5» из
референса и «как-то» остаются целыми.

**Разошлось между референсами — значит свобода, а не правило:**

- брендовая плашка PRO NEIRO стоит в первом референсе как ОБЫЧНАЯ сцена, в слоте
  карточки и с подписью под ней («ССЫЛКЕ», «БЕСПЛАТНО»), а не только концовкой;
- концовка во втором держится 3.3 с (59.0 → 62.35), у нас `OUTRO_SECONDS=2`;
- маскот бывает не только «вместо карточки», но и поверх неё, выглядывая сбоку;
- две соседние сцены могут делить одну иллюстрацию с небольшим изменением;
- внутри иллюстраций встречается текст («Google», «2030»). У нас он запрещён
  промптом — и запрет остаётся: генераторы рисуют буквы ненадёжно, а «2030» в
  кадре стоит меньше, чем риск кракозябр;
- темп речи: второй референс отдаёт 2.33 слова в секунду, наш ролик 2.75 — мы
  на 18% быстрее.

Про частоту кадров: первый референс 60 fps, второй 30. Верить этому нельзя —
пережатие могло проредить кадры, и проверить это по результату невозможно.

### Фоновой музыки в референсе нет

Проверялось, потому что «сделать такой же музыкальный фон» — очевидное
пожелание. Замеры по 7 присланным частям и ещё 4 роликам того же агентства:

- в паузах между фразами низы падают на 20-30 дБ (−49…−63 дБ при −22…−34 дБ под
  речью) — непрерывного баса нет;
- устойчивых тональных линий нет: пик низов в каждой паузе приходится на другую
  частоту (129, 105, 70, 270, 258 Гц), это остатки голоса, а не нота;
- выше 500 Гц в паузах остаётся 0.2% мощности — ни хэтов, ни «воздуха»;
- дорожка практически моно (корреляция каналов +0.94…+0.998), стереофонической
  подложки нет.

Единственный низкочастотный «бум» в паузе — стингер стыка, они у нас уже
воспроизведены. То есть в референсе под речью **тишина**, и это осознанный
приём: музыка конкурирует с голосом на телефонном динамике.

За «плотность» там отвечает не музыка, а громкость: все 11 роликов лежат на
**−9.8…−12.2 LUFS** при разбросе громкости (LRA) 0.8-1.8 LU. Наш первый ролик
измерялся на **−14.6 LUFS / LRA 3.2**. Поэтому после рендера добавлен проход
выравнивания (`src/bot/masterAudio.ts`, `MASTER_LUFS`, по умолчанию −12): явное
усиление плюс лимитер, замер тем же прибором (`ebur128`), видео копируется
потоком. На том самом ролике: −14.6 → −12.0 LUFS, пик −1.3 dBTP.

Почему не `loudnorm`: наш микс пиками уже у нуля, а поднять надо на 2-3 дБ; в
такой ситуации линейный режим `loudnorm` молча переключается на динамический и
начинает править разброс громкости — делает не то, что просили. Отдельная
засада — `alimiter`: по умолчанию у него `level=enabled`, то есть выход
домножается на `1/limit` и пик возвращается к нулю, отменяя заданный потолок.
Замером видно: без `level=disabled` выход шёл на +0.1 dBTP вместо −1.5.

Что осталось несведённым с референсом — разброс громкости: у нас 3.2 LU против
их ~1.2. Это уже компрессия, а не усиление, и на слух её здесь проверить нельзя.

### Библиотека музыки: свои треки и подготовка

Треки можно **присылать в чат**: `/addmusic` (или кнопка «Загрузить свои треки» в
`/music`) — дальше файлы идут по одному, подряд, пока не придёт `/done`. Годятся
аудиофайлы и видео (дорожка вытаскивается через `extractAudio`), а файлы больше
20 МБ — ссылкой на Drive: больше Telegram боту не отдаёт. Проверено на настоящих
mp3, m4a, ogg и mp4.

Имя файла в библиотеке собирается из присланного, но от него остаётся только
основа без папок и без всего, кроме букв, цифр, дефиса и подчёркивания: имя
приходит от пользователя и становится путём на диске, поэтому «../» или кавычка в
нём не должны ни увести запись из папки, ни сломать список файлов. Метка времени
— чтобы два файла с одинаковым названием не затирали друг друга.

Каждый присланный трек проходит ту же подготовку, что и сгенерированный.

### Подготовка треков

Если музыку под речь вы всё-таки хотите (это отличие ОТ референса, а не
приближение к нему), треки надо готовить, а не просто складывать в папку.
`/music` → «Привести треки к порядку» делает это над всей библиотекой, а
сгенерированные треки проходят подготовку сразу:

- **Одна громкость на все треки** (−16 LUFS). Раньше её задавал источник: Suno
  отдаёт около −8 LUFS, а файл, положенный руками, мог быть −20 — при одном
  множителе в миксе это двенадцать децибел разницы, то есть один трек звучал
  фоном, а другой помехой. Множитель `MIX.music` теперь тоже выведен, а не
  подобран: трек −16 LUFS при 0.145 садится на 18 дБ ниже речи (голос в нашем
  миксе меряется около −14.8 LUFS). Прежнее 0.06 работало по случайности —
  ровно потому, что Suno отдаёт громкие мастера.
- **Место под голос**: низ ниже 60 Гц убран (там живут удары стыков), полоса
  разборчивости речи 2-4 кГц приглушена на 3 дБ.
- **Бесшовная петля.** Remotion повторяет файл целиком, и на стыке конца с
  началом слышен щелчок. Лечится переносом хвоста в начало: результат длиной
  D−X, где первые X секунд — начало трека, смешанное с его затухающим хвостом.
  Тогда на стыке волна продолжается, а не прыгает: R(0) = orig(D−X), а перед
  стыком звучит orig(D−X−ε).

Три вещи выяснились только замером, и все три ломали результат молча:

1. **Громкость надо ставить ДО склейки петли.** У `alimiter` есть предпросмотр,
   и первые миллисекунды файла он отдаёт тишиной — то есть ровно ломает
   непрерывность, которую склейка создаёт (начало обработанного файла меряется
   на 7 против 3965 в середине). После склейки остаётся только статическое
   усиление.
2. **`amix` двух ветвей одного входа отдаёт длину КОРОТКОЙ ветви.** Трек на 16
   секунд превращался в 2, и `duration=longest` на это не влияет. Те же две
   части, но отдельными файлами, смешиваются правильно.
3. **Длину для склейки надо брать у промежуточного wav, а не у исходного mp3.**
   В длительности mp3 сидит тишина выравнивания кадра, и склейка по чужой длине
   уезжает на десятки миллисекунд — на стыке это уже слышно.

Готовые треки лежат в wav. Не потому, что mp3 «ломает петлю»: я так сначала и
написал, а потом замерил — ffmpeg честно снимает задержку кодера по тегам LAME,
провала на стыке нет. Но зависит это от того, учитывает ли теги декодер, а
Remotion декодирует в Chromium, и его поведение отсюда проверить не удалось. wav
снимает вопрос, а библиотека всё равно лежит только на сервере.

### Чужой трек: обмерить можно, поставить нельзя

Вытащенный из чужого ролика минус — чужая запись, и в свои ролики она не идёт.
Законный путь — обмерить его и заказать генератору свой трек в том же темпе и
тональности. Это делает кнопка под результатом `/stems`, а обмер лежит в
`src/pipeline/analyzeMusic.ts`: темп, тональность, доли по полосам, громкость.
Описание для генератора собирается из чисел, показывается в чате и попадает в
подпись к готовому треку вместе со сверкой (темп и тональность полученного
против образца).

Определитель писался с тремя ошибками, и каждую поймали синтезированные треки с
ЗАРАНЕЕ ИЗВЕСТНЫМИ темпом и тональностью — на чужой музыке все три выглядели бы
правдоподобно:

- **Высота автокорреляции не годится как уверенность в пульсе.** У чистого дрона
  она выходит 0.94, у трека с бочкой — 0.90; то есть по ней «пульс» находится
  там, где его нет. Работает контраст всплесков энергии (p95/медиана): дрон 2.9,
  речь 2.8, бочка 2300.
- **Кадр 1024 не разрешает полутон в басах.** Бин при 22 кГц — 21.5 Гц, а полутон
  у 185 Гц — 10.7 Гц: нота размазывается по бинам, которые ближе к F и G, чем к
  F#, и «D# minor» уверенно определялся как «F major». Нижняя граница хромы
  теперь выводится из разрешения (полтора бина на полутон), а кадр взят 8192.
- **Мощность вместо магнитуды даёт тональность бочки, а не трека.** В квадрате
  один громкий удар перевешивает весь аккорд.

Заодно и сам тест был неправ дважды: бочка в нём стояла на фиксированных 55 Гц
независимо от тональности (то есть добавляла ноту, которой в трезвучии нет), а
бас был чистым синусом без гармоник — в регистре, где основной тон не
разрешается, читать тональность просто не по чему.

### Проверить это ушами: /stems

Вывод «музыки нет» получен замерами, а его хочется услышать. У ElevenLabs для
этого есть отдельный эндпоинт — `POST /v1/music/stem-separation`: дорожка
разбирается на стемы, в режиме `two_stems_v1` это голос и «минус». Команда
`/stems` в боте принимает видео, аудио или ссылку на Drive, присылает стемы
файлами и сразу показывает громкость каждого: если минус тише голоса больше чем
на 25 дБ, под речью не музыка, а шум и звуки стыков. `/stems six` дробит на шесть
(вокал, барабаны, бас, остальное) — пригодится, если музыка всё-таки нашлась и
надо понять, из чего она собрана.

Обратите внимание: вытащенный минус — чужая запись. Он годится понять, что там
играет, и повторить это своей генерацией; ставить его в свои ролики нельзя.

Контракт запроса сверен с официальным SDK (`@elevenlabs/elevenlabs-js` 2.59.0,
`resources/music/client/Client.js`): файл полем `file`, режим полем
`stem_variation_id`, формат — query-параметром `output_format`, ответ — zip.
Живым ключом из песочницы проверить нельзя (`api.elevenlabs.io` недоступен),
поэтому мок в `test:stems` повторяет контракт буквально и придирается к каждому
полю — но первый настоящий вызов всё равно остаётся первым.

Zip разбирается своим кодом (`src/pipeline/unzip.ts`, оглавление плюс stored и
deflate) — без новой зависимости и без системного `unzip`, которого на сервере
может не оказаться: такое падение вылезло бы уже в рантайме на живом ключе.
Имена внутри архива приходят от сервиса, поэтому берётся только базовое: «../» в
имени не должен писать мимо папки.

Первая сцена — **хук**, и подача у неё отдельная: карточка видна с первого
кадра (он же обложка в ленте) и доезжает упругим наездом, а в самом начале
играет подъём с ударом (`public/sfx/hook.wav`). Сам текст хука пишется по жёстким правилам и
проверяется автоматически — см. «Хук» ниже.

Картинка внутри карточки генерируется через Kie.ai
(`src/pipeline/generateImage.ts`) по описанию стиля (`STYLE_PROMPT`),
выведенному из кадров референса: плоская векторная иллюстрация, толстый
чёрный контур, приглушённая пастельная палитра. Текста в кадре быть не должно
(`NO_TEXT_RULE`): текст в ролике рисует Remotion чистым шрифтом — это субтитры
по словам, — и надпись внутри картинки конкурировала бы с ними, тем более что
кириллицу картиночные модели рисуют с ошибками. По той же причине подпись сцены
не попадает в промпт: увидев готовую фразу, модель норовит её нарисовать,
поэтому сцена описывается только текстом озвучки.

Фирменный маскот "Pro Neiro" — джин **Шамиль (Шама)**. Его эталонное
изображение лежит в `assets/characters/shamil.png` и прикладывается к запросу
как референс внешности (лицо, причёска, одежда, цвета) вместе с текстовым
описанием `CHARACTER_PROMPT` — так модели проще держать персонажа узнаваемым.

**Но не в каждой сцене.** Раньше эталон шёл в каждый запрос, и джин лез в кадр
даже там, где сцена про серверы или про космос: ролик превращался в галерею поз
одного персонажа. Теперь он в хуке (лицо ролика) и в финале (призыв к действию
говорит именно он), а середина — про содержание истории и рисуется без него
(`sceneWithCharacter()`, `NO_CHARACTER_PROMPT`). В референсе так же: иллюстрации
в основном без маскота, он появляется отдельным слоем в ключевых местах.
`CHARACTER_EVERY_SCENE=1` возвращает прежнее поведение.

Важно, что вместе с описанием убирается и приложенная картинка-эталон: она
сама по себе сильный сигнал, и модель тянет персонажа в кадр, даже если промпт
просит обойтись без него. По той же причине описание маскота вообще не идёт в
промпт появляющегося объекта — там нужен предмет.

Kie.ai принимает входные картинки только по публичной ссылке, поэтому эталон
передаётся ссылкой на файл в этом репозитории (raw.githubusercontent.com).
Если сделаете репозиторий приватным — выложите картинку в другое публичное
место и укажите адрес в `CHARACTER_REFERENCE_URL`.

Важная оговорка: это приближение через промпт + референс-изображение, не
точная копия. Консистентность персонажа не гарантирована на 100% и зависит
от возможностей image-модели. Если результат расходится с ожиданиями —
`STYLE_PROMPT` в `generateImage.ts` стоит донастраивать по факту (например,
уточнить типовые ракурсы/позы Шамиля), а `assets/characters/shamil.png`
можно заменить на более "чистый" референс без логотипа лампы, если он
будет мешать генерации.

## Маркетинговые проверки сценария

Разбор первого настоящего ролика дал пять претензий, и четыре из них
проверяются машиной — теми же средствами, что хук и реклама: найденное уходит
модели на переписывание.

**Тема обязана вести к продукту.** Ролик был про то, сколько электричества
жрёт обучение нейросетей, а финал — «попробуй наш бот для генерации
картинок». Между ними нет моста: зритель никогда не собирался обучать модель,
эта боль не его, и финал читается как «а теперь реклама». Проверить машиной
нельзя — правило живёт в промпте, а бот перед отрисовкой спрашивает прямо:
если закрыть последнюю сцену, зритель догадается, что ему сейчас предложат?
Если нет, тема выбрана мимо, и правкой текста это не чинится.

**Яркая цифра должна быть в хуке** (`hookNumberProblem`). «1287 мегаватт-часов,
это как сто домов за год» стояло на двенадцатой секунде — к этому моменту
половина зрителей уже ушла. Проверка ищет крупные числа и слова масштаба
(миллион, мегаватт, процент) в середине при пустом хуке. Год из подсчёта
исключён: «в 2026 году» есть в каждом втором ролике про ИИ и крючком не
является.

**Финал содержательной части должен давать вывод** (`deadEndProblem`).
«Инженеры и учёные ищут способы… это непростая задача» — не вывод, а
разведённые руки: уносить нечего, спорить не о чем, пересылать незачем, то
есть отключены ровно те сигналы, по которым площадка решает, показывать ролик
дальше. Смотрим предпоследнюю сцену — в последней идёт призыв, и там те же
слова были бы уместны.

**Призыв — одно конкретное предложение** (`ctaProblem`). «Наш бот соберёт
фото, видео, музыку. Загляни по ссылке, там много интересного» — так говорит
каждый второй ИИ-бот, и «там много интересного» не обещает ничего. Проверка
требует конкретики (бесплатно, без регистрации, попробуй сейчас), запрещает
вежливые пустышки и держит призыв в 22 словах: в присланном ролике он занял
двенадцать секунд, шестую часть хронометража.

**Примеры должны быть свежими** (`staleProblem`). Флагманский пример — GPT-3,
то есть 2020 год: для аудитории, которая следит за темой, это как сослаться
на позапрошлый айфон. Список устаревших названий приходится обновлять руками,
других способов нет — зато вреда от него меньше, чем от ролика с примером
пятилетней давности.

Ещё три правила ушли в промпт, потому что проверке не поддаются: один тон на
весь ролик (одно сленговое слово посреди энциклопедического текста звучит как
чужая заплатка), актуальность примеров и читаемость вслух — синтезатор
произносит текст слово в слово, и «это как сто домов год» будет произнесено
именно так.

Отдельный тест держит инвариант: **пример стиля в промпте проходит все
проверки, которые мы предъявляем модели**. Пример сильнее правил, и слабый
пример научил бы ровно тому, что мы запрещаем.

### Критик вместо регулярок: правила вкуса вынесены из кода

Проверки выше выведены из разбора одного ролика, и на потоке тем это тупик:
каждая новая тема приносит свои обороты. Регулярка найдёт «непростую задачу»,
но не найдёт «ну, посмотрим, куда это всё вырулит» — а это ровно та же пустая
концовка. Список либо отстаёт, либо начинает браковать здоровое, и каждая
правка требует программиста и деплоя.

Поэтому проверки разделены на два вида.

**Структура остаётся в коде** — ритм, бюджет слов, длина хука, реклама не в
финале, перечисление сервисов. Это объективные вещи, они не зависят от темы и
не устаревают. Выключить их нельзя.

**Смысл проверяет модель-критик** (`src/pipeline/reviewScript.ts`) по
чек-листу, который лежит **текстовым файлом** `data/review-checklist.md`.
Критик получает чек-лист, бриф и сценарий, возвращает список претензий — и они
уходят в тот же механизм автоправки, что и структурные. Переписывать он не
пытается: это работа сценариста, у которого есть весь контекст.

Чек-лист правится **из чата командой `/rules`** — прислали новый текст, он
применился к следующему сценарию. Ни программиста, ни деплоя. `/rules reset`
возвращает исходный.

Критик — улучшение, а не условие работы: если OpenRouter недоступен или
ответил мусором, сценарий идёт дальше с одними структурными проверками, а бот
пишет об этом в чат. Ронять генерацию, за которой следуют оплаченные картинки,
из-за критика нельзя.

Регулярки вкуса при этом остались и включены по умолчанию: они бесплатны и
детерминированны. `SCRIPT_TASTE_RULES=0` оставит только критика — так имеет
смысл работать, когда тем много и списки шаблонов начинают мешать больше, чем
помогают.

### Корпус здоровых сценариев — защита от подгонки

Все эти правила выведены из разбора **одного** ролика, и это главный риск:
проверка, подогнанная под единственный случай, начинает браковать нормальные
сценарии на других темах. Поэтому в `test:script` лежит корпус из шести
заведомо хороших сценариев на разные темы — с цифрами и без, с историческими
ссылками, с призывом через подписку вместо «бесплатно». Ни один не должен
вызывать ни одной претензии; отдельно проверяется обратное — что больной
сценарий по-прежнему бракуется по всем пунктам.

Корпус окупился сразу же, забраковав три правила из четырёх:

- «тысячи вариантов» считалось яркой цифрой — я обобщил конкретное
  «1287 мегаватт-часов» до любого слова масштаба. Теперь слово масштаба
  считается крючком только рядом с цифрой;
- «это непростая задача, **поэтому** начни с одного инструмента» —
  законный финал с выводом — попадал под «кончается ничем». Добавлено
  исключение на прямое указание зрителю;
- «тогда GPT-3 удивлял всех» — историческая ссылка, а не устаревший пример.
  Не считается, если рядом есть маркер прошедшего времени;
- заодно вскрылось расхождение: промпт разрешал подпись хука в 8 слов, а
  проверка требовала 5 — модель следовала инструкции и получала отказ.

Добавляя новое правило, добавляйте и случай в корпус: цена ложного
срабатывания — лишнее переписывание сценария и, что хуже, ухудшение
нормального текста.

## Ритм: сцена — это кадр, а не законченная мысль

Первый настоящий ролик вышел **71 секунда при лимите 60, шестью сценами**.
Замер по кадрам: одна картинка провисела 15 секунд с покадровой разницей 0.06
из 255 — то есть абсолютно неподвижно. В референсе картинка меняется каждые
полторы-три секунды, и вся работа над переходами (восемь механик входа, рваная
шторка, зум-блюр, звуки на стыках) при шести склейках на ролик просто не видна.

Причин было три, и они усиливали друг друга:

1. **Правило в промпте** прямо просило «оптимально 5-7 сцен» и «сцены-объяснения
   по 25-45 слов». При 2.1 слова в секунду 45 слов — это 21 секунда одного
   кадра.
2. **Пример стиля** показывал пять сцен, одна на шестьдесят слов. Пример сильнее
   правил: модель копировала именно его. Теперь тот же текст разбит на
   тринадцать кадров, и видно главное — фраза может обрываться на середине и
   продолжаться в следующей сцене.
3. **Проверки не было вовсе.** `totalWords` встречался только внутри текста
   промпта; вернулся сценарий в бюджет или нет, никто не смотрел. Ровно та же
   болезнь, что была у лимита описания в 500 символов.

Теперь сцена — это **кадр**: 8-14 слов, то есть 4-6.7 секунды. Последней сцене
с призывом к действию можно вдвое больше — рвать призыв пополам незачем, да и
проверка на рекламу освобождает только последнюю сцену.

`rhythmProblem()` меряет **длину сцены, а не их количество**. Считать сцены
заманчиво, но это привязка к длине ролика: три сцены на пятнадцать секунд —
нормальный ритм, а три сцены на минуту — беда. Слова переводятся в секунды
напрямую, и порог работает одинаково на ролике любой длины. Найденное уходит
модели на переписывание тем же механизмом, что хук и реклама.

Отдельный тест проверяет, что **пример стиля сам проходит проверку, которую
предъявляет модели**. Он её и не прошёл с первого раза — 133 слова при бюджете
126.

Скорость речи снижена с 2.4 до **2.1 слова в секунду** — по тому же замеру:
ролик вышел на 19% длиннее бюджета. Ошибаться в эту сторону дороже, чем в
обратную: недобор длины никому не мешает, а перебор ломает лимит, и подрезать
его уже нечем — `fitToBudget` умеет только урезать паузы, а это доли секунды
на сцену.

## Что говорит ролик: история, а не реклама

Жанр — «рассказываю интересное»: свежая новость, неожиданный факт, разбор
«как это вообще работает». Структура жёсткая: хук → сама история → и лишь
последняя сцена про продукт.

- **В промпте** описан жанр и лежит эталонный пример целиком (ролик про
  дата-центры Маска на орбите, который заказчик прислал как образец). По
  живому примеру модель держит тон и плотность заметно лучше, чем по списку
  правил: середина — это механика истории (в чём был тупик, как его обходят,
  какая деталь всё меняет), а не пересказ возможностей продукта. Продукт,
  бренд, подписка, тарифы и ссылки запрещены везде, кроме финала.
- **Тон** — живой разговорный, на «ты», со сленгом и риторическими
  вопросами. Это не противоречит запрету на воду: живой тон — конкретика,
  сказанная по-человечески, а вода — восторг вместо содержания.
- **Цифры** из физики и техники («минус 270», размер радиатора) приветствуются
  — они и есть суть истории. Запрещены только рекламные: проценты, «в N раз»,
  «за N минут».
- **Середина — приёмы, а не список сервисов.** Самый частый провал: ролик
  превращается в перечисление названий («Midjourney сделает раскадровку»,
  «Suno напишет музыку») — зритель не выносит ни одного действия. В промпте
  на это есть пары примеров «плохо/хорошо», а `toolListProblem()` считает,
  сколько сцен середины — просто названия инструментов: больше двух и больше
  40% сцен — повод переписать. Названий на весь ролик допускается не больше
  двух, и только вместе с деталью применения.
- **Никакой воды.** `fillerProblem()` ловит пустой восторг («красота»,
  «чистый кайф», «бомбически»), штампы («легко и просто», «меняет дело»,
  «в два клика»), связки без содержания («сначала мы идею в текст заносим»,
  «как говорится», «да?») и непроверяемые цифры — проценты, «в N раз»,
  «за N минут», в том числе числами-словами.
- **Реклама только в финале.** `promoProblem()` ищет рекламные обороты во всех
  сценах, кроме последней: «наш бот», «у нас есть», подписка, тарифы,
  промокод, «ссылка в описании», «жми/переходи».
- Все найденные проблемы уходят модели **одной** правкой, каждая со своей
  инструкцией, и показываются в чате.
- **Меньше сцен — больше пользы**: промпт рекомендует 5-7 сцен и задаёт бюджет
  словами на весь ролик (≈2.4 слова в секунду), а не нормой на каждую сцену.
  Жёсткая норма на сцену как раз и превращала сценарий в телеграф: при 15
  сценах на реплику остаётся четыре слова, и объяснить в них нечего.
  Распределение неравномерное — хук короткий, сцены-объяснения по 25-45 слов.

Лимит длины задаётся на чат командой **`/length <секунды>`** (15-120) и
переопределяет `MAX_VIDEO_SECONDS`. Он нужен в двух местах сразу: сценарист
считает из него бюджет слов, а сборка — предел для подгонки паузами. Ролик с
плотными объяснениями в минуту не всегда влезает: присланный образец — 159 слов,
это ≈66 секунд, так что под такой формат разумно поставить 70-80 с (Reels,
Shorts, TikTok и VK Клипы это принимают).
- **Актуальность** обеспечивает веб-поиск OpenRouter (`SCRIPT_WEB_SEARCH=1`):
  без него «свежие модели и тренды» ограничены датой обучения модели. Поиск
  подключается только к первому запросу — на правках тема уже выбрана и
  тратить его незачем. Если плагин недоступен, запрос автоматически уходит
  без него, а бот честно предупреждает, что данные не свежие.
- **Сноски из поиска вырезаются.** С включённым веб-поиском модель дописывает
  к фразам источники (`[mashagpt.ru](https://…)`) — в подписи это мусор, а в
  озвучке синтезатор читает адрес вслух. `stripSources()` убирает ссылки,
  голые домены и сноски `[1]` из всех текстов сценария, аккуратно подчищая
  осколки пунктуации; названия моделей вида GPT-5.4 при этом не страдают.

## Появляющиеся объекты: картинка не меняется, объект прилетает

Сцена может показать что-то новое, не меняя картинку целиком: поверх той же
иллюстрации появляется отдельно сгенерированный предмет с прозрачным фоном —
ровно в тот момент, когда его называет озвучка.

- **Сценарист** сам предлагает предмет: в схеме ответа у сцены есть
  необязательное поле `overlay: {object, word}` — что нарисовать и на каком
  слове реплики это должно появиться. Промпт требует именно предмет («монета»,
  «спутниковый радиатор с рёбрами»), а не сцену или действие, и просит ставить
  объект примерно в половине сцен, чтобы приём не надоел.
- **Прозрачность делается у нас, а не моделью.** У nano-banana альфа-канала
  нет вовсе, у gpt-image параметры прозрачности не описаны — поэтому объект
  рисуется на сплошном ярко-зелёном `#00FF00`, а фон вырезается ffmpeg
  (`src/pipeline/chromaKey.ts`). Способ работает с любой моделью.

  Два подводных камня, на которые я наступил: порядок фильтров важен — сначала
  `colorkey`, и только потом `despill` (наоборот `despill` перекрашивает сам
  фон, и вырезать становится нечего), а обрезка по границам объекта считается
  в Node по сырым пикселям альфы — фильтра «обрежь по альфе» в ffmpeg нет, а
  `cropdetect` работает по яркости и на прозрачном фоне даёт мусор.
- **Момент появления** берётся из таймингов слов (`overlayStartMs`): слово
  ищется по корню, потому что сценарист пишет его в начальной форме, а в
  реплике оно склоняется. Не нашлось — объект появляется в первой трети сцены.
- **В кадре** объект лежит внутри карточки, поверх картинки: обрезается её
  рамкой, имеет тень (иначе читается как наклейка) и прилетает упругим
  наскоком с последующим лёгким покачиванием. Угол чередуется по номеру сцены.
- **Если объект не получился** — например, модель залила зелёным весь кадр —
  сцена собирается без него, а бот пишет причину. Объект показывается в чате
  на согласовании: если модель вместо предмета нарисовала целую сцену или
  добавила персонажа, это видно сразу, и объект можно перегенерировать.

Цена: одна дополнительная генерация картинки на сцену с объектом.

## Оживление кадров: сцена может быть не картинкой, а клипом

В референсе не все сцены статичны — часть из них живёт, и именно эти секунды
удерживают внимание. У нас это делается не генерацией сцены с нуля, а
анимацией той картинки, которая для сцены уже нарисована и уже согласована в
боте: она идёт **первым кадром** клипа (image-to-video, Seedance через
Kie.ai).

Почему именно так, а не отдельной генерацией видео по тексту:

- стиль не «уплывает» — движение начинается ровно с утверждённого кадра;
- оживить можно выборочно, не трогая остальные сцены;
- если генерация не удалась, сцена просто остаётся картинкой — ролик, в
  котором уже оплачены картинки и озвучка, из-за клипа не теряется.

Маскота в промпт клипа не тянем: оживает то, что в сцене уже нарисовано. Нет
персонажа в кадре — оживает предмет или место, и это нормально.

**Камера в промпте просится неподвижной.** Карточка в кадре и так приезжает
анимацией; если внутри неё ещё и поедет камера, стык перестаёт читаться — то
же самое выяснилось раньше про наезд на картинку.

**Клип короче сцены** (обычно 2 с против трёх). Остаток сцены досиживает на
последнем кадре клипа, а не повторяет его с начала: повтор виден как рывок,
замершая сцена читается как «движение улеглось». Длина клипа меряется у файла
через `ffprobe` — модели округляют её по-своему. Проверено рендером: на кадре
сцены 45 в карточке стоит 0.750 с клипа, на кадре 110 — 0.983 с, то есть его
последний кадр (`CLIP_RENDER_TEST=1 npm run test:clips`).

**Сколько сцен оживлять — команда `/clips`,** по умолчанию ноль. Это
единственная настройка, которая заметно меняет стоимость ролика, и цену она
считает по выбранной модели: между Mini и полной 2.0 разница больше чем
вдвое, а длительность модель может поднять до своего минимума — цифра «за две
секунды» врала бы в полтора раза. Первым оживляется хук, вторым финал, дальше — середина равномерно,
чтобы движение не сгрудилось в начале. Готовые клипы кэшируются в сессии:
повторная сборка после сбоя не оплачивает их заново.

**Про слаги и поля — история одной ошибки.** Первую версию я написал по
догадке: слаги вида `bytedance/seedance-v2-mini-i2v`, входная картинка в поле
`image_url`, длительность 2 секунды. Живой прогон `/vidmodel probe` вернул
422 «The model name you specified is not supported» на все три кандидата, и
при разборе выяснилось, что неверным было не только имя:

| что | было | стало |
| --- | --- | --- |
| слаг | `bytedance/seedance-v2-mini-i2v` | `bytedance/seedance-2-mini` |
| картинка | `image_url` | `first_frame_url` (у Seedance 2.x) |
| длительность | 2 с | 4 с — короче Seedance 2 не умеет |

То есть даже угадай я слаг, запрос всё равно не прошёл бы дважды. Семейств
теперь два, и вход у них разный: Seedance 2.x берёт `first_frame_url` +
`aspect_ratio` + `generate_audio`, а Seedance V1 — `image_url` + `camera_fixed`
(у него неподвижность камеры прямо выключателем, а не просьбой в промпте).
Длительность приводится к допустимому диапазону модели (`clampClipSeconds`),
чтобы просьба о двух секундах не отвергалась молча.

**`/vidmodel probe` устроена вокруг несимметричной цены ошибки.** Отказ
бесплатен: Kie.ai отвечает на `createTask` 422 сразу, задача не создаётся,
поэтому перебирать кандидатов можно свободно. А успех — это уже настоящая
оплаченная генерация, так что перебор останавливается на первой рабочей
модели. Пробуем минимальной допустимой длительностью: проба на секунду
отвергалась бы и у верного слага, то есть врала бы.

Осталась одна невыясненная мелочь — регистр буквы в разрешении: примеры
документации для V1 написаны строчной (`720p`), описания Seedance 2 —
прописной (`720P`). Значение вынесено в `CLIP_RESOLUTION`, чтобы чиниться
правкой `.env`, а не передеплоем.

Рабочий слаг можно вписать в `KIE_VIDEO_MODEL`, но с оговоркой: эта
переменная перебивает реестр целиком, и выбор модели через `/vidmodel`
перестаёт на что-либо влиять. Поэтому в `.env.example` она пустая, а бот
предупреждает, если она заполнена.

## Эталон внешности: почему лицо не совпадало

Первые клипы библиотеки вернули непохожего персонажа, и виноват был не
промпт, а эталон. `assets/characters/shamil.png` — рекламный стикер: персонаж
с лампой и надписью PRO NEIRO, наклеенный на **фотографию офиса**. Как вход
для image-to-video он плох сразу по трём причинам:

1. **Лицо занимает 18% высоты кадра.** На выходе 720p это меньше шестидесяти
   пикселей на лицо — сохранять там нечего, и модель рисует его заново.
   Это главная причина.
2. **Фон — фотография, а промпт просит однотонный светлый.** Модель обязана
   перерисовать фон, а перерисовывая кадр, заодно перерисовывает персонажа.
3. **В кадре надпись PRO NEIRO** — при том, что текст в кадре мы сами
   запрещаем отдельным правилом.

`npm run character:ref` собирает из него `shamil-clip.png`: стикер отделён от
фотографии по сплошной белой обводке (фон — связная область не-белых пикселей,
дотягивающаяся до края кадра, находится разметкой связных компонент), лампа
отрезана по самому узкому месту дымного хвоста, остаток кадрирован в 3:4 по
персонажу. Лицо стало **34% высоты — вчетверо больше пикселей** при том же
разрешении вывода, поза со скрещёнными руками сохранена, фон уже белый.
Исходник остался в репозитории.

Пропорции эталона ровно 3:4, как у карточки, и это не косметика: при другом
соотношении модель перекадрирует вход, а перекадрирование — это тоже
перерисовка.

Побочный эффект, который пришлось закрыть отдельно: белый фон эталона мог
переехать в картинки сцен, где нужно настоящее окружение. В `CHARACTER_PROMPT`
теперь прямо сказано, что фон эталона служебный и образцом не является.

Если лицо всё равно плывёт, есть второй рычаг: **`CLIP_LOCK_IDENTITY=1`**
отдаёт тот же эталон ещё и последним кадром (Seedance 2 умеет режим «первый и
последний»), и персонаж обязан к концу вернуться ровно к нему. Держит крепче,
но движение становится «туда и обратно»: жест возвращается в исходную позу.
По умолчанию выключено — сначала стоит посмотреть, хватит ли нового эталона.

## Библиотека клипов с маскотом: платим один раз

Оживление сцены стоит денег в каждом ролике. Но маскот в любом ролике делает
одно и то же — появляется, удивляется, показывает, прощается, — и эти клипы
от темы не зависят. Поэтому их десять, они генерируются **один раз** и дальше
подставляются бесплатно:

```bash
npm run clips:build                # сгенерировать недостающие
npm run clips:build -- --force     # пересобрать всё
npm run clips:build -- intro-lamp  # только один
```

Пересобирать всё ради одного клипа незачем, поэтому и команда, и скрипт
понимают роль или конкретные идентификаторы: `/library build intro` тронет
только три клипа хука, `/library rebuild intro-snap` — ровно один. Непонятное
слово отвергается целиком, а не пропускается молча: молча пересобрать не то,
что просили, значит потратить чужие деньги.

Из чата: `/library` показывает состояние, `/library <id>` присылает клип
посмотреть. Если клип переписан под новым идентификатором, старый файл
остаётся лежать — он оплачен, и удалять его сам я не берусь, но `/library`
его показывает отдельным списком, чтобы библиотека не обрастала мусором
незаметно.

Состав — четыре роли, и встают они туда же, где по нашему правилу и так
появляется маскот (хук и финал):

| роль | где | варианты |
| --- | --- | --- |
| `intro` | хук | подаётся к зрителю, щёлкает пальцами, хитрая улыбка |
| `reaction` | середина | задумывается, удивляется, кивает |
| `handoff` | середина | протягивает предмет, показывает в сторону |
| `outro` | финал | большой палец и подмигивание, уходит в лампу |

**Клипы хука не строятся на появлении персонажа** — он в кадре с первого
кадра и сразу что-то делает. Первая версия была другой: джин выходил из
лампы, проявлялся из дымки, влетал в кадр. Это ошибка замысла, а не
исполнения — карточка хука в тот же момент сама приезжает упругим наездом, и
появление внутри неё давало два появления подряд, гасящих друг друга. Мы уже
наступали на эти грабли со стыками (`coversFrame`). Причина та же, по которой
хук не проявляется, а врубается: первый кадр ролика — это ещё и обложка в
ленте, и он должен быть непустым.

Вариантов хука три, а не два, намеренно: хук есть в каждом ролике, и с одним
вариантом все ролики начали бы открываться одинаково. Внутри одного ролика
клип не повторяется — занятые запоминаются; выбор среди готовых случайный,
но происходит при сборке данных и попадает в `video-data.json`, поэтому
рендер остаётся повторяемым.

**Порядок «сначала библиотека, потом генерация»** задаётся `CLIP_SOURCE`:
`auto` (по умолчанию) — готовый клип, если он есть, иначе платная генерация;
`library` — только готовые, ни одной платной генерации; `generate` — всегда
оживлять картинку сцены. Это самое дорогое место фичи, поэтому порядок
закрыт тестом: он кладёт в библиотеку настоящий файл и проверяет, что клип
взялся оттуда, а в Kie.ai никто не пошёл.

Фон в промпте библиотечного клипа просится пустым и светлым: клип встаёт в
ту же карточку, что и иллюстрации, и дорисованное моделью окружение выбивало
бы его из общего ряда. Сами файлы лежат в `assets/clips/` и в репозиторий не
кладутся — это десяток видеофайлов, а собрать их заново можно одной командой.

## Субтитры по словам, переходы, акценты, смаз

**На стыке одновременно виден только один субтитр.** Уходящее слово гасло за
40% длины стыка и ещё читалось, когда слово входящей сцены уже проявилось: на
настоящем ролике я поймал кадр, где «МОДЕЛЕЙ.» и «ПРИКОЛ» напечатаны друг
поверх друга на одной строке. Обе сцены рисуют субтитры на одном базовом
уровне, поэтому пересекаться им нельзя вообще — теперь уходящее гаснет за 12%
стыка, то есть за два-три кадра из восемнадцати. Проверено рендером до и
после.


Всё это — пакеты Remotion, подключённые к нашему шаблону.

- **Субтитры «по слову»**: под карточкой в кадре ровно **одно** слово — крупно,
  заглавными, чёрным по белому, без плашки и без анимации. Слово просто меняется
  на следующее в такт речи, это и есть весь приём. Так сделано в референсе:
  геометрия снята с его кадров (1440×2560) и приведена к нашему 1080×1920 —
  высота заглавных букв 77 px, низ строки на 23% высоты от нижнего края кадра,
  по центру (`src/remotion/Subtitles.tsx`). Это единственный текст в кадре:
  статическую подпись под картинкой убрали, чтобы не было двух надписей сразу.

  Тайминги берутся из озвучки, а не из распознавания: прямой ElevenLabs умеет
  возвращать выравнивание по символам вместе со звуком (`/with-timestamps`), из
  него собираются слова (`src/pipeline/wordTimings.ts`). Через прокси Kie.ai
  таймингов нет — тогда слова раскладываются по длине реплики пропорционально
  числу букв: приближение, но на коротких фразах расхождение незаметно.
  Отключается `WORD_SUBTITLES=0`.

  Слово для кадра выбирает `wordAt` (`src/remotion/subtitleWord.ts`) — последнее
  из начавшихся, а не «то, чей интервал содержит время»: между словами бывают
  паузы, и в них кадр не должен оставаться без текста. Раньше здесь были
  «страницы» из нескольких слов с подсветкой текущего (и своя разбивка вместо
  `createTikTokStyleCaptions`, которая группирует по **паузам**, а у слитных
  таймингов пауз нет) — от этого отказались: в референсе другой приём.

- **Готовые переходы** (`@remotion/transitions`): часть стыков делает не наша
  анимация карточки, а переход всего кадра — шторка снизу, переворот в 3D,
  круговая развёртка. Пресентации библиотеки рассчитаны на `TransitionSeries`,
  но он сдвигает тайминги, а у нас на них завязана озвучка — поэтому
  компоненты пресентаций используются внутри наших `Sequence`
  (`src/remotion/CutTransition.tsx`). На таком стыке своё движение карточки
  отключается: два перехода поверх друг друга дают кашу.

- **Формы и текст** (`@remotion/shapes`, `@remotion/paths`): по одному акценту
  на сцену — искра, звезда, кольцо или стрелка, которая «прочерчивается»
  штрихом (`evolvePath`). Все живут в полосе над карточкой: карточка занимает
  82% ширины и рисуется поверх, поэтому акцент рядом с ней просто не виден —
  первая версия почти целиком ушла под неё.

- **Motion blur** (`@remotion/motion-blur`): смаз включается только на кадрах
  входа и ухода — `CameraMotionBlur` рендерит поддерево несколько раз, и держать
  его на всём ролике незачем. Замер на 500 кадрах разницы во времени рендера не
  показал (34.3 с против 34.5 с): смазанных кадров мало. Оборачивать нужно
  сцену целиком — сам компонент рендерит `AbsoluteFill`, и если завернуть в него
  только карточку, та выпадает из потока. Выключается `motionBlurEnabled: false`
  в данных ролика.

- **Studio** (`npm run preview`): две композиции. `VideoComposition` — реальный
  ролик из `data/video-data.json` с редактируемыми через zod-схему пропсами;
  `MotionLab` — стенд из восьми сцен, по одной на каждый вариант движения,
  включая библиотечные переходы и акценты. Стенд не требует ни картинок, ни
  генерации: правите анимацию и сразу видите результат.

## Хук

Первые 1-2 секунды решают, досмотрят ролик или пролистнут, поэтому хук в
первой сцене обязателен и не отдаётся на волю модели.

- **В промпте** (`buildSystemPrompt` в `src/pipeline/generateScript.ts`)
  первая сцена описана отдельным блоком: запрещены приветствия,
  представления и «в этом видео», озвучка — не больше 12 слов, подпись — до
  5 слов, плюс список рабочих приёмов (боль зрителя, неожиданное
  утверждение, вопрос в лоб, обещание результата).
- **После генерации** сценарий проходит проверку `hookProblem()`: слабое
  начало ловится регуляркой (модель про запрет иногда забывает), считаются
  слова в озвучке и подписи. Если хук не годится, `generateCheckedScript()`
  делает одну целевую правку — просит переписать только первую сцену,
  остальные оставить как есть. Причина правки уходит в лог CLI и в чат бота
  («✏️ Переписал: …»), так что видно, что именно не понравилось.
- **Вторая попытка не зацикливается**: если и переписанный хук слаб, берётся
  тот сценарий, что есть — пустой результат хуже слабого.
- **Подача** хука усилена в кадре и в звуке (см. раздел про стиль выше).

## Голос

Озвучка идёт моделями ElevenLabs — либо через прокси Kie.ai (по умолчанию),
либо напрямую (`/tts elevenlabs`, нужен `ELEVENLABS_API_KEY`).

Параметры похожести задаются в `.env` (`TTS_*`) и одинаковы для обоих путей:
`similarity_boost` 0.9 держит тембр исходной записи, `style` 0 не даёт модели
«играть» и уводить от оригинала, `stability` 0.4 оставляет живую интонацию, а
`use_speaker_boost` (только прямой путь) добавляет сходства с оригинальным
голосом.

**Клонированный голос работает только напрямую.** Клон живёт в вашем аккаунте
ElevenLabs, а Kie.ai обращается к ElevenLabs со своего — вашего голоса он не
видит, и ролик будет озвучен другим. Бот проверяет это сочетание сам
(`cloneViaProxyWarning`): если выбран не базовый голос, а провайдер остался
`kie`, перед озвучкой придёт предупреждение с подсказкой `/tts elevenlabs`.
Какой именно голос активен, показывает `/voice` — он спрашивает имя у
ElevenLabs, так что видно, тот ли это клон.

Про качество самого клона: мгновенное клонирование (Instant Voice Cloning)
делает похожий голос от минуты чистой речи, а на 20-30 секундах с музыкой на
фоне получается лишь отдалённое сходство. Поэтому в боте есть `/clone`: он
вытаскивает дорожку из ваших роликов, убирает фон через ElevenLabs Voice
Isolator и склеивает несколько фрагментов в один сэмпл.

Материал можно добавить и в уже готовый клон — `/clonemore`. Важно, что
мгновенный клон при этом не «дообучается»: ElevenLabs пересчитывает отпечаток
голоса по всему набору сэмплов заново.

В запрос уходит только новый материал. Прежние сэмплы бот всё равно скачивает,
но как страховку: если набор внезапно заменится, старый материал не пропадёт —
бот пришлёт его файлами в чат. Сначала прежние сэмплы отправлялись обратно
вместе с новым, ровно чтобы набор не заменился, — и живой API ответил на это
`400 duplicated_files`, «You cannot upload the same file twice». Этой ошибкой он
же и закрыл вопрос, который в документации не описан: `POST /v1/voices/{id}/edit`
**дополняет** набор сэмплов, а не заменяет его — иначе сравнивать присланное с
уже лежащим в голосе не имело бы смысла. Прежние сэмплы должны остаться на месте,
и бот это проверяет по их `sample_id` после обновления.

Побайтовые повторы отсеиваются заранее, причём в момент приёма файла, а не на
`/done`: так видно, какой именно файл лишний, и ничего не теряется. Прислать один
ролик дважды несложно — сбор идёт по одному файлу и переживает ошибки, — а
ElevenLabs на повтор отвечает отказом и валит всю операцию.

После обновления бот показывает, как изменился состав:
сколько сэмплов и секунд было и стало. Отдача от добавления быстро выходит на
плато: заметный шаг вперёд — это уже Professional Voice Cloning с 30+ минутами
записи, и он делается только в кабинете ElevenLabs.

**Про предел 11 МБ на файл.** ElevenLabs принимает загружаемые файлы не больше
11 МБ и на превышение отвечает `400 upload_file_size_exceeded`. Наступить на это
легко и незаметно: 434 секунды речи, вернувшиеся от Voice Isolator, весят 16,5 МБ
— то есть предел пробивается не объёмом материала, а битрейтом ответа (около
320 кбит/с), и вместе с отказом терялась вся собранная сессия. Поэтому перед
загрузкой файлы приводятся к тому, что примет API (`voiceSamples.ts`):

- файл в пределах лимита не трогается вовсе — материал, из которого считается
  отпечаток голоса, не стоит лишний раз перекодировать;
- файл больше лимита сначала пережимается в моно 192 кбит/с (для речи с запасом,
  а по размеру ровно 24 КБ/с — куски считаются без сюрпризов). Тот самый случай
  на 434 секунды после этого влезает одним файлом;
- если и после пережатия не влезает, режется на равные части. Части считаются от
  их нужного числа, а не «по столько-то секунд подряд»: иначе у дорожки на 434
  секунды при пределе 432 последним куском отваливается огрызок на две секунды, и
  как сэмпл голоса он бесполезен. Границы файлов внутри набора роли не играют —
  отпечаток считается по набору целиком.

Тот же предел действует и на очистку от музыки, а материал на клон собирается из
нескольких роликов и перерастает 11 МБ ещё до неё. Длинная дорожка чистится по
частям и склеивается обратно.

## Как приходит готовый ролик

- **Файлом, а не видео.** `sendVideo` Telegram перекодирует под стриминг, и
  качество теряется; документ доходит байт в байт. Обложку для файла бот делает
  сам (ffmpeg, кадр из начала, 320 px по высоте — таково требование Telegram),
  иначе ролик выглядит в чате безымянным вложением.
- **Рендер идёт с CRF 20** — раз перекодирования на стороне Telegram больше нет,
  качество исходника и есть то, что увидит зритель. Если файл не влезает в лимит
  бота, он сжимается отдельно (см. ниже).
- **Вместе с видео приходит текст описания** под публикацию: отдельным
  сообщением, чтобы его можно было скопировать целиком, не выцепляя из подписи
  к файлу. В подписи остаются только факты о файле: размер кадра, длительность,
  вес.

### Текст описания

Пишется по готовому сценарию (`src/pipeline/generateDescription.ts`), потому что
описание должно обещать ровно то, что в видео.

- Структура: зацепка из ролика → 2-3 коротких абзаца по сути → призыв к
  действию → 3-5 хештегов. Эмодзи обязательны, но как маркеры абзацев, а не
  гирлянда.
- **Длина — не больше 500 символов, это жёсткое правило.** Гарантируется не
  промптом, а обрезкой на выходе (`enforceLimit`): промпт модель может
  проигнорировать дважды, сеть может отвалиться на повторной попытке, а предел
  должен держаться всё равно. Режется при этом тело, а не хвост — хештеги стоят
  последней строкой и нужны для поиска, поэтому они сохраняются целиком, а обрыв
  ставится по границе слова и помечается многоточием. Если урезать пришлось, бот
  пишет об этом в чате: обрезанный хвост стоит перечитать глазами.
  `DESCRIPTION_CHARS` (450 по умолчанию) — это **цель** для промпта, и она
  специально ниже предела: если просить ровно 500, модель через них
  перескакивает. Значение из `.env` прижимается к диапазону 350-450.
- `descriptionProblem()` проверяет результат: длину, наличие эмодзи и хештегов,
  отсутствие ссылок (за внешние ссылки в описании площадки занижают охват) и
  markdown-разметки. Одна повторная попытка с указанием причины.
- Если модель недоступна или упрямо отдаёт мусор, описание собирается из самого
  сценария (`fallbackDescription`) — лучше короткий честный текст, чем пустое
  поле. В чат приходит пометка, что текст запасной.
- Чистка сносок веб-поиска здесь идёт **построчно**: общий `stripSources`
  схлопывает пробелы, а в описании переводы строк — это абзацы. На этом
  первый вариант и сломался, теперь есть тест.

В CLI-пайплайне описание пишется в `out/description.txt`.

## Размер файла и лимит Telegram

Бот отправляет файлы не больше **50 МБ** — на большем Telegram отвечает
`413: Request Entity Too Large` уже после загрузки, и ролик, за который
заплачены генерации, остаётся лежать на сервере. Поэтому:

- рендер идёт с `--crf=20` вместо стандартного 18 — файл заметно легче при
  почти неотличимой картинке (на трудном для сжатия материале CRF 23 давал
  261 МБ против 507 МБ у значения по умолчанию);
- перед отправкой бот смотрит размер и, если тот больше 45 МБ, перекодирует
  ролик под лимит (`src/bot/videoSize.ts`): битрейт считается из длины, а
  разрешение и длительность не меняются — для соцсетей это незаметнее, чем
  уменьшенный кадр;
- если даже так не выходит без заметной потери качества (очень длинный ролик),
  бот честно предлагает сократить сценарий или забрать файл с сервера:
  `scp root@ip:~/Amg/out/video.mp4 .`

`npm run test:clips` по умолчанию не рендерит: он проверяет логику (какие
сцены оживляются, что реестр моделей собирает вход правильно, что длина клипа
берётся у файла). Проверку самого рендера — что клип играет внутри карточки и
что после его конца кадр замирает, а не повторяется с начала — включает
`CLIP_RENDER_TEST=1`; она занимает несколько минут, потому что рендерит четыре
кадра настоящим Remotion. Если браузер Remotion скачать некуда, путь к
готовому Chromium передаётся через `REMOTION_BROWSER`.

`npm run test:kie` поднимает фальшивый сервер Kie.ai и проверяет асинхронный
цикл (создание задачи → опрос статуса → скачивание результата) и обработку
ошибок: отказ задачи, пустой результат, таймаут. Реальные запросы к API не
уходят, кредиты не тратятся.

## Форматы под площадки

Частота кадров — 60 (`VIDEO_FPS`). Резкие стыки длятся 0.3 с, и на 30 кадрах
это всего 9 кадров: движение читается рвано. В референсе тоже 60. Платим
временем рендера — оно примерно удваивается; `VIDEO_FPS=30` возвращает как было.

По умолчанию — вертикальный формат 1080×1920 (Reels/Shorts/TikTok/VK
Клипы). Меняется через `VIDEO_WIDTH`/`VIDEO_HEIGHT` в `.env`; для
горизонтального YouTube-формата можно рендерить тот же шаблон повторно с
1920×1080 — раскладка сцены рассчитана на `AbsoluteFill` и подстроится под
любые пропорции без правок кода.

## Заметки по инструментам

- **OpenRouter** (сценарий): модель задаётся через `OPENROUTER_MODEL` (по
  умолчанию `anthropic/claude-sonnet-5`). Список ID моделей может меняться,
  актуальный — на openrouter.ai/models.

  Почему не самая дешёвая: сценарий — единственный шаг, где решается, будет ли
  ролик смотрибельным, а стоит он копейки на фоне остального. Один сценарий —
  порядка $0.03 (наш системный промпт ~8.5 КБ плюс выдача веб-поиска на входе,
  ~1к токенов на выходе; Sonnet 5 — $2/$10 за 1M вводной ценой), тогда как 15
  картинок на Nano Banana Pro — около $1.35. То есть модель сценария это ~5% от
  стоимости ролика. Дешёвый вариант, если он всё же нужен:
  `OPENROUTER_MODEL=google/gemini-2.5-flash` (~$0.006 за сценарий).

  `response_format: json_object` — параметр из мира OpenAI, и не всякая модель
  на OpenRouter его принимает. Поэтому запрос повторяется без него, а JSON
  достаётся разбором (`extractJson`): снимается ```-блок и отбрасывается текст
  вокруг. Это зафиксировано тестом, так что модель можно менять свободно.
- **Резервная озвучка**: прокси Kie.ai для моделей ElevenLabs бывает
  нестабилен (отдаёт свои `internal error` при работающей генерации картинок
  тем же ключом). На этот случай есть прямой путь к ElevenLabs — добавьте
  `ELEVENLABS_API_KEY` в `.env` и переключитесь командой `/tts elevenlabs`
  в боте (или `TTS_PROVIDER=elevenlabs`).
- **Kie.ai** (озвучка + картинки): один ключ `KIE_API_KEY` на оба сервиса.
  API асинхронный — задача создаётся, потом опрашивается до готовности; вся
  эта логика в `src/pipeline/kie.ts`. Модели задаются через `KIE_TTS_MODEL`
  и `KIE_IMAGE_MODEL`, голос — через `KIE_TTS_VOICE`. Названия моделей и
  доступные голоса сверяйте в кабинете Kie.ai: они меняются.
- Для картинок нужна модель, принимающая входные изображения (image-to-image,
  по умолчанию `google/nano-banana-edit`) — иначе эталон персонажа не будет
  учитываться и Шамиль перестанет быть похожим на себя.
- Права на дизайн/анимацию из заказанных у агентства видео стоит уточнить
  по договору, прежде чем воспроизводить их 1:1.
